# Технический стек — «Яйцо в Храме»

## Решение в одной строке

Базовый стек: **Vite + TypeScript + Three.js + Rapier**. Игра запускается локально в одном браузере для двух игроков на одной клавиатуре. Colyseus остаётся документированным следующим этапом и не входит в базовую версию.

Архитектура локального режима должна сохранить чёткую границу между вводом, симуляцией и отображением, чтобы онлайн можно было добавить позже без переписывания визуала, уровней, механик яйца или коллекции птенцов.

## Архитектура базовой версии

```text
Клавиатура двух игроков
            ↓
InputManager → локальная симуляция Rapier
                         ↓
               состояние игроков, яйца и механизмов
                         ↓
             Three.js-сцена + камера + DOM-интерфейс
```

**Правило MVP:** физика выполняется в браузере. Оба игрока управляются с одной клавиатуры; сервер и сетевые адаптеры не создаются.

## Границы первой версии

| Режим | Входит в первую версию | Что откладывается |
|---|---|---|
| Локальный кооператив | Да: 2 игрока, одна клавиатура, один браузер | — |
| Онлайн-кооператив | Нет | Colyseus-комната на 2 игроков, приглашения и переподключение — следующий этап |
| Аккаунты, рейтинг, магазин | Нет | Коллекция птенцов сохраняется локально; аккаунты нужны только для переноса её между устройствами |
| Мобильная версия | Нет | Оптимизация управления и производительности отдельно |

## Рекомендуемый стек

| Задача | Инструмент | Почему именно он |
|---|---|---|
| Язык | **TypeScript** | Типы снижают число ошибок в механиках, физике и сетевых сообщениях. |
| Сборка и локальная разработка | **Vite** | Быстрый dev-сервер, горячее обновление и оптимизированная production-сборка; не требует тяжёлого фреймворка. |
| 3D-рендер | **Three.js** | Подходит для low-poly сцены: модели, свет, тени, материалы, постобработка и камера в браузере. |
| Физика | **Rapier (`@dimforge/rapier3d-compat`)** | Одна физическая библиотека на клиенте и сервере для яйца, персонажей, наклонов, шипов и подъёмников. |
| Игровая логика | Собственные TypeScript-системы | Для двух персонажей и одного яйца отдельный игровой движок или ECS только усложнит проект. |
| UI | HTML/CSS поверх `<canvas>` | Шкала прочности, пауза, подсказки и меню проще, доступнее и быстрее делать в DOM. |
| Локальное сохранение | **localStorage** с версией схемы | Хранит открытых птенцов, лучшее время и лучший результат без аккаунта и сервера. |
| 3D-ассеты | **Blender → glTF/GLB** | Бесплатный понятный путь для low-poly моделей; один компактный формат загрузки в Three.js. |
| Звук | Web Audio API + аудиофайлы | Достаточно для эффектов, музыки и регулировки громкости без отдельной библиотеки. |
| Проверка качества | ESLint + Prettier + Vitest | Единый стиль кода и быстрые тесты правил уровня / состояния игры. |
| Развёртывание MVP | Cloudflare Pages или Netlify | Статическая Vite-сборка разворачивается без серверной инфраструктуры. |

## Целевые платформы базовой версии

- Актуальные стабильные версии Chrome и Edge на ПК.
- Минимальное разрешение: **1280×720**.
- Целевая производительность: **60 FPS** на современном ноутбуке.
- Сетевая часть и Node.js-сервис не запускаются и не развёртываются в базовой версии.

## Игровой цикл базовой версии

```text
Клавиатура двух игроков
    ↓
InputManager ──→ команды игроков ──→ Rapier physics
                                       ↓
                                 состояние мира
                                       ↓
             Three.js scene + камера + HTML/CSS HUD
```

### Ключевое правило

**Локальная физика — источник истины в MVP.** Three.js только отображает положение объектов. Каждый кадр игра:

1. считывает клавиши обоих игроков;
2. передаёт команды движения и взаимодействия в локальную симуляцию;
3. обновляет Rapier фиксированным шагом `1/60` секунды;
4. копирует физические позиции в 3D-модели Three.js;
5. обновляет UI и звук.

Так яйцо, шипы, склоны и подъёмники ведут себя предсказуемо, а визуальная часть не ломает геймплей.

## Техническая реализация механик

| Механика | Реализация |
|---|---|
| Яйцо | Динамическое сфероидное тело Rapier с прочностью, ограничением максимальной скорости и событиями столкновений. |
| Игроки | Кинематические тела или character controller Rapier; толчок яйца выполняется силой только в сторону движения игрока. |
| Падение и урон | Датчики (sensors) на шипах и проверка силы столкновения / вертикальной скорости перед приземлением. |
| Кнопки | Датчики с проверкой цвета игрока или веса яйца; состояние меняет мосты и двери. |
| Рычаги | Объекты взаимодействия с короткой анимацией; доступные действия показываются в DOM-HUD. |
| Подъёмники | Кинематические платформы, двигающиеся по заданному маршруту; яйцо и игроки остаются обычными физическими телами. |
| Контрольная точка | Чистые данные: позиции игроков, яйца, активные механизмы и прочность. Повторная загрузка пересоздаёт физический мир из снимка. |
| Камера | Three.js OrthographicCamera или перспектива с очень малым углом обзора; плавно следует за яйцом и ограничена рамками уровня. |
| Вылупление и коллекция | Финиш запускает короткую Three.js-анимацию фрагментов скорлупы; `CollectionService` записывает ID открытого птенца и лучший результат в `localStorage`. |

## Рендер и арт-пайплайн

- Модели создаются в Blender, намеренно с малым числом полигонов и крупными гранями.
- Экспортировать в **GLB**: один файл проще загружать, версионировать и кэшировать.
- Сначала использовать простые материалы Three.js с vertex colors; текстуры добавлять только там, где они заметно улучшают картинку.
- Неоновый стиль строить светом, emissive-материалами, цветным туманом и умеренным bloom-эффектом. Bloom включать только после замера производительности.
- Ограничить число динамических источников света; большинство теней и атмосферы имитировать запечёнными цветами / простыми материалами.
- Целевой бюджет MVP: стабильные 60 FPS на современном ноутбуке, один видимый уровень, до 30 активных физических объектов.

## Почему не Unity, Unreal, React или полноценный ECS

- **Не Unity / Unreal:** для небольшой браузерной игры они добавляют тяжёлую сборку, размер загрузки и сложность публикации. Арт-референс вдохновлён качеством UE5, но не требует UE5 как движка.
- **Не React для игрового мира:** React хорош для меню, но не нужен для покадровой сцены. Обычный DOM достаточно надёжен для HUD.
- **Не Phaser:** он отличен для 2D, но здесь ценность игры — объёмный low-poly свет и ландшафт.
- **Не ECS сразу:** у игры мало сущностей и систем. Обычные классы и модули проще отлаживать; ECS можно добавить только при реальной необходимости.
- **Не онлайн в MVP:** сетевую физику, комнаты, приглашения, друзей, рейтинг и голосовой чат добавлять только после плейтестов локальной версии.

## Онлайн-кооператив: следующий этап (не входит в MVP)

| Слой | Выбор | Роль |
|---|---|---|
| Game server | Node.js + TypeScript + **Colyseus** | Комнаты на двух игроков, матчмейкинг, переподключение и синхронизация состояния. |
| Авторитетная симуляция | Rapier на сервере | Сервер единолично считает физику яйца, игроков и механизмов; клиент не может подменить результат. |
| Связь | WebSocket через Colyseus | Клиенты отправляют только ввод; сервер отправляет подтверждённое состояние. |
| Клиентская плавность | Интерполяция + локальное предсказание персонажа | Скрывает сетевые задержки, не меняя истину игры. |
| Хранение | Сначала без БД | Комнаты и прогресс живут только в сессии. БД нужна лишь для аккаунтов или сохранений. |

```text
Игрок 1: ввод ─┐                         ┌─→ состояние → Игрок 1
               ├─→ Colyseus room ─→ Rapier ┤
Игрок 2: ввод ─┘       (сервер)          └─→ состояние → Игрок 2
```

### Почему сервер считает яйцо

Два клиента не смогут надёжно синхронно рассчитывать сложные столкновения физического яйца. В онлайн-режиме сервер принимает только действия игроков (`двигаться`, `прыгать`, `взаимодействовать`) и на фиксированном шаге рассчитывает результат. Это защищает совместную головоломку от рассинхронизации и нечестного клиента.

Colyseus подходит для этого этапа: его модель Room изолирует отдельные игровые сессии, а серверные изменения состояния автоматически передаются клиентам как дельты.

## Что не добавлять до первых плейтестов

- Базу данных, вход через социальные сети и профили.
- Микросервисы, Kubernetes, Redis и отдельный API-шлюз.
- Генерацию уровней, редактор уровней в браузере и моды.
- Сложные шейдеры, ray tracing, трассировку физики «как в симуляторе».
- Голосовой чат: для тестов достаточно Discord / системного звонка.

## Порядок разработки базовой версии

1. Создать проект Vite + TypeScript и пустую Three.js сцену.
2. Добавить Rapier, плоскость, двух персонажей и яйцо; добиться приятного толкания.
3. Реализовать шипы, падение, прочность, контрольную точку и рестарт.
4. Добавить один уровень, кнопки, рычаг, мост и подъёмник.
5. Добавить low-poly модели, фиолетово-розовый свет, огромный светящийся диск солнца и звук.
6. Провести локальный плейтест с двумя людьми и исправить непонятные моменты управления.
7. Добавить сцену вылупления, локальную коллекцию птенцов и сохранение лучших результатов.

## Минимальные команды

```bash
npm create vite@latest egg-temple -- --template vanilla-ts
cd egg-temple
npm install three @dimforge/rapier3d-compat
npm install -D typescript eslint prettier vitest
npm run dev
```
